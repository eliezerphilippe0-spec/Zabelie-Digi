# Rapport de revue — Zabelie — 2026-07-27

**Mode** : COMPLET · **Périmètre** : UX, UI, Sécurité, Responsivité — application
entière · **Stack** : Next.js 16.2.10 (App Router, Turbopack) + Supabase
(Postgres 17 / Auth / Storage / RLS) + Vercel · **Branche** :
`claude/zabelie-talent-context-85ph4j`

---

## Résumé exécutif

Le money-path est la partie la mieux tenue de cette application, et de loin :
RLS active sur **toutes** les tables, `search_path` épinglé sur **toutes** les
fonctions `security definer`, clé `service_role` jamais côté client, signature
Stripe vérifiée, retour MonCash confirmé serveur-à-serveur avec limitation de
débit, montant revérifié en base, ledger protégé en append-only par déclencheur.
Ce n'est pas courant à ce stade d'un projet.

Les trois risques les plus urgents ne sont pas là où l'on regarde d'habitude :

1. **La qualification juridique de la rétention des fonds n'est pas tranchée**
   (REG-01). Ce n'est pas un défaut de code — c'est le seul point qui peut
   arrêter la plateforme, et il grossit avec chaque vendeur recruté.
2. **L'application n'a aucun écran d'erreur, aucun écran de chargement, aucune
   page 404** (UX-01) : zéro fichier `error.tsx`, `not-found.tsx`, `loading.tsx`
   dans tout `app/`. Sur un lien WhatsApp ouvert en 3G, la moindre panne
   serveur donne l'écran par défaut de Next, en anglais, sans porte de sortie.
3. **Aucun en-tête de sécurité HTTP** (SEC-01) et **trois vulnérabilités haute
   sévérité** dans les dépendances (SEC-02), dont `next` lui-même.

Un mot sur le contexte, parce qu'il change la lecture de tout le reste : la
production porte **0 commande et 1 compte**. Aucun constat de ce rapport n'a
encore blessé personne. C'est la fenêtre où les corriger est gratuit.

## Constats détaillés

### 🔴 Critiques

#### [REG-01] La rétention des fonds vendeurs n'a pas de qualification juridique
- **Axe** : Sécurité — positionnement réglementaire
- **Emplacement** : `docs/17-DOSSIER-BRH-RETENTION.md` ; mécanisme dans
  `supabase/migrations/0001_schema.sql:98` (`wallets.owner_id`) et
  `supabase/migrations/0027_coupon_consume_on_confirm.sql:109-120`
- **Constat** : la plateforme encaisse sur un compte marchand unique, mêle
  fonds vendeurs et revenus propres sans cantonnement, et retient le net
  vendeur jusqu'au règlement manuel. Le dossier est ouvert et **sans réponse à
  ce jour**.
- **Impact** : ce n'est pas un risque d'amende, c'est un risque d'existence —
  détenir l'argent d'autrui sans base juridique établie. L'exposition croît
  linéairement avec le nombre de vendeurs recrutés.
- **Preuve** : vérifié que le positionnement *topup* est respecté (aucun solde
  acheteur : `wallets` est indexé sur `owner_id` vendeur, et
  `app/api/checkout/route.ts` ne débite aucun solde). L'écart ne porte donc
  pas sur la recharge mais sur la **rétention marketplace**.
- **Correctif proposé** : obtenir l'avis écrit **avant 50 vendeurs, pas avant
  500**. Aucune ligne de code ne le remplace.
- **Effort** : L (juridique, hors code)

### 🟠 Élevés

#### [SEC-01] Aucun en-tête de sécurité HTTP
- **Axe** : Sécurité
- **Emplacement** : `next.config.mjs:1-14`
- **Constat** : la configuration ne déclare aucune fonction `headers()`. Ni
  `Content-Security-Policy`, ni `X-Frame-Options`, ni
  `X-Content-Type-Options: nosniff`, ni `Referrer-Policy`.
- **Impact** : la fiche produit et le tunnel de paiement peuvent être placés
  dans une `iframe` tierce (clickjacking sur le bouton d'achat) ; aucune
  défense en profondeur si une XSS apparaît un jour. Sur un produit distribué
  par liens WhatsApp, l'encadrement d'une page dans un site tiers est le
  scénario réaliste.
- **Preuve** : `grep -n "headers\|Content-Security" next.config.*` → aucun
  résultat. Le fichier ne contient que `reactStrictMode` et `images`.
- **Correctif proposé** : ajouter un bloc `async headers()` avec au minimum
  `X-Frame-Options: DENY` (ou `frame-ancestors 'none'`), `nosniff` et
  `Referrer-Policy: strict-origin-when-cross-origin`. Une CSP complète demande
  un inventaire des sources — la faire en second temps.
- **Effort** : S pour les trois premiers, M pour la CSP

#### [SEC-02] Trois vulnérabilités haute sévérité, dont `next`
- **Axe** : Sécurité
- **Emplacement** : `package.json` (dépendances de production)
- **Constat** : `npm audit --omit=dev` remonte 3 vulnérabilités **haute**
  sévérité : `next` (>=9.3.4-canary.0), `postcss` (<=8.5.17), et `sharp`
  (<0.35.0, CVE-2026-33327 / 33328 / 35590 / 35591 héritées de libvips).
- **Impact** : dépend de chaque CVE ; `next` et `sharp` traitent
  respectivement les requêtes entrantes et les images téléversées par les
  vendeurs — deux surfaces exposées.
- **Preuve** : sortie de `npm audit --omit=dev`, correctif annoncé disponible
  via `npm audit fix`.
- **Correctif proposé** : appliquer `npm audit fix`, relancer la suite
  complète (118 tests TS + SQL + e2e) et le build avant de fusionner. La règle
  du dépôt interdit une dépendance **nouvelle** sans validation ; une montée de
  version corrective n'est pas dans ce cas, mais mérite le même passage par la
  PR.
- **Effort** : S

#### [UX-01] Aucun écran d'erreur, de chargement ou de page introuvable
- **Axe** : UX (et Responsivité — voir impact 3G)
- **Emplacement** : arborescence `app/` — `find app -name "error.tsx"` → **0**,
  idem `global-error.tsx`, `not-found.tsx`, `loading.tsx`
- **Constat** : les quatre états d'écran que la grille exige ne sont couverts
  qu'au cas par cas dans certains composants. Au niveau des routes, aucun.
- **Impact** : trois conséquences distinctes.
  1. **Erreur serveur** → écran par défaut de Next, en anglais, sans lien de
     retour. Sur un lien WhatsApp, c'est la dernière impression laissée.
  2. **URL inexistante** (fiche supprimée, lien partagé périmé) → 404 générique
     au lieu d'une porte vers le catalogue.
  3. **Navigation en 3G** → les pages sont en `force-dynamic` et rendues côté
     serveur ; sans `loading.tsx`, l'écran précédent reste figé plusieurs
     secondes sans aucun indicateur. L'utilisateur re-tape.
- **Preuve** : `app/page.tsx:81-86` documente déjà le problème en commentaire —
  « l'accueil n'a pas cette page d'erreur, il n'y a AUCUN `app/error.tsx` dans
  le projet », et contourne par un `.catch(() => [])`.
- **Correctif proposé** : trois fichiers, contenu en i18n : `app/error.tsx`
  (message + « Réessayer » + retour catalogue), `app/not-found.tsx`,
  `app/loading.tsx` (squelette sobre). Le plus rentable du rapport au ratio
  effort/impact.
- **Effort** : M

#### [UX-02] Le paiement exige un compte
- **Axe** : UX
- **Emplacement** : `app/api/checkout/route.ts:84-86`
- **Constat** : `supabase.auth.getUser()` puis `401 Authentification requise`.
  Aucun parcours invité.
- **Impact** : un lien WhatsApp qui tombe sur un formulaire d'inscription perd
  une grande part des visiteurs — et ce mur n'a **jamais été franchi par
  personne** (1 compte en production). Sa hauteur réelle n'est pas mesurée.
- **Preuve** : lecture de la route ; aucune branche invité.
- **Correctif proposé** : découpler compte et commande, en gardant la
  contrainte héritée de `0043` — **jamais de commande sans contact
  joignable enregistré**, sinon l'auto-réception d'expédition perd sa
  légitimité et l'escrow peut se verrouiller. Le compte devient optionnel, le
  champ contact ne l'est pas. À chronométrer avant de coder.
- **Effort** : L

### 🟡 Moyens

#### [SEC-03] Aucune garde contre l'achat de son propre produit
- **Axe** : Sécurité
- **Emplacement** : `app/api/checkout/route.ts:114` (le `seller_id` est bien
  lu) — mais aucune comparaison avec `user.id` dans toute la route
- **Constat** : rien n'empêche un vendeur d'acheter sa propre fiche.
- **Impact** : vecteur de *wash trading* — un vendeur peut gonfler son nombre
  de ventes et ses avis. **Sans conséquence tant qu'aucun classement ni
  aucune mise en avant ne s'appuie sur le volume**, ce qui est le cas
  aujourd'hui. Devient 🟠 le jour où « meilleures ventes » existe.
- **Preuve** : `grep -n "seller_id" app/api/checkout/route.ts` → lignes 114,
  170, 171, 174 ; toutes concernent le produit et les coupons, aucune
  comparaison d'identité.
- **Correctif proposé** : refuser en `403` si `product.seller_id === user.id`.
  ⚠️ **À poser AVANT tout classement par volume, pas après.**
- **Effort** : S

#### [SEC-04] Une fonction `security definer` non révoquée
- **Axe** : Sécurité
- **Emplacement** : `supabase/migrations/0045_profile_on_signup.sql:199-202`
- **Constat** : `zabelie_handle_new_user()` est `security definer` et ne porte
  pas de `revoke all on function … from public, anon, authenticated`, alors
  que c'est la convention systématique du dépôt (vérifié sur 0046, 0047, 0048).
- **Impact** : **faible en pratique** — c'est une fonction `returns trigger`,
  et PostgreSQL refuse son appel direct hors contexte de déclencheur. Le
  constat porte sur la rupture de convention, pas sur une exploitation.
- **Preuve** : la fonction déclare `returns trigger` (ligne 200) ;
  `search_path` est bien épinglé (vérifié : aucune `security definer` du dépôt
  n'en manque).
- **Correctif proposé** : ajouter le `revoke` par cohérence — une exception
  non expliquée dans un fichier finit par en autoriser une autre.
- **Effort** : S

#### [UX-03] Le formulaire de vente physique est en français codé en dur
- **Axe** : UX (Kreyòl-first)
- **Emplacement** : `components/physical-product-form.tsx` — libellés,
  aides et messages d'erreur écrits directement dans le JSX, sans passer par
  `lib/i18n.ts`
- **Constat** : c'est la surface vendeur du chantier physique, et elle est
  monolingue sur une plateforme dont la langue première est le Kreyòl.
- **Impact** : le vendeur ciblé — commerçant de pièces auto, de vêtements —
  est précisément celui qui lit le moins le français administratif.
- **Preuve** : lecture du composant ; seules les deux additions récentes
  (estimation du net, lien vers les règles) passent par i18n, via des libellés
  fournis par la page serveur.
- **Correctif proposé** : extraire les chaînes vers `lib/i18n.ts` sur le même
  patron que `publish-form.tsx` (objet `labels` fourni par la page serveur).
  Le test de parité FR/HT existant (`tests/i18n.test.ts`) couvrira
  automatiquement les nouvelles clés.
- **Effort** : M

#### [UI-01] Le contrôle de contraste ne mesure pas les couleurs réellement affichées
- **Axe** : UI
- **Emplacement** : `scripts/zabelie-contrast.mjs:46,72` et
  `app/zabelie-theme.css:30-46`
- **Constat** : le thème déclare explicitement que les jetons de **base**
  (`--color-success`, `--color-danger`, …) ne doivent **jamais** servir de
  couleur de texte, et fournit des variantes `*-text` pour cela. Or le script
  mesure les jetons de base — et **aucune** des variantes `-text`. Ses
  « 7 paires sous le seuil » sont donc du bruit attendu, tandis que les paires
  effectivement affichées ne sont mesurées par personne.
- **Impact** : un contrôle qui échoue toujours cesse d'être lu ; et la question
  qu'il devrait trancher — les textes affichés passent-ils WCAG AA ? — reste
  sans réponse automatisée.
- **Preuve** : `grep -n "success" scripts/zabelie-contrast.mjs` → `success:
  "#8FBF6F"` (base) ; aucune occurrence de `successText` / `#9ac57d`. Calcul
  manuel effectué sur une paire réelle (`success-text` sur fond composité) :
  ≈ 9,7:1, largement conforme — mais calculé à la main, pas par l'outil.
- **Correctif proposé** : ajouter les variantes `-text` à la liste mesurée et
  reclasser les jetons de base en seuil 3:1 (usage pastille/graphique), pour
  que le script rende vert quand tout va bien.
- **Effort** : S

### 🔵 Faibles

#### [SEC-05] Les routes d'administration renvoient le message d'erreur brut
- **Axe** : Sécurité
- **Emplacement** : `app/api/admin/refund/route.ts:35`,
  `app/api/admin/coherence/route.ts:42`, `app/api/admin/confirm-zelle/route.ts:66`,
  `app/api/admin/topup/refunds/route.ts:65`,
  `app/api/admin/topup/confirm-zelle/route.ts:64`,
  `app/api/admin/search-demand/route.ts:57`
- **Constat** : `return NextResponse.json({ error: error.message }, …)` expose
  le message PostgreSQL au client.
- **Impact** : **limité** — toutes ces routes exigent un rôle `admin` ou un
  secret de cron (vérifié : aucune route sous `app/api/admin/` n'échappe à ce
  contrôle). La divulgation se fait donc à un administrateur. Le constat vaut
  surtout comme discipline.
- **Correctif proposé** : journaliser le détail côté serveur, rendre un
  message générique — patron déjà appliqué aux routes de création de fiche.
- **Effort** : S

#### [UI-02] Une couleur hors palette
- **Axe** : UI
- **Emplacement** : `app/layout.tsx:52`
- **Constat** : `#17123a` en dur (couleur de thème du navigateur), sans
  correspondance dans `app/zabelie-theme.css`.
- **Impact** : cosmétique ; la barre du navigateur mobile ne s'accorde pas
  exactement au fond de l'application.
- **Correctif proposé** : la faire pointer sur un jeton existant.
- **Effort** : S

#### [RES-01] Cibles tactiles secondaires sous 44 px
- **Axe** : Responsivité
- **Emplacement** : boutons secondaires en `py-2` / `py-2.5`
  (`components/publish-form.tsx`, `components/buy-button.tsx`)
- **Constat** : hauteur effective ≈ 36–40 px, sous le seuil recommandé de
  44×44. Les actions **principales** sont en `py-3` / `py-3.5` (≈ 44–48 px) et
  sont conformes.
- **Impact** : imprécision au pouce sur petit écran, sur des actions
  secondaires uniquement.
- **Correctif proposé** : passer les cibles interactives à `py-3` minimum.
- **Effort** : S

## Ce qui est solide — et mérite d'être dit

Un rapport qui ne liste que des défauts donne une image fausse. Vérifié
explicitement, sans exception trouvée :

- **RLS active sur les 19 tables** du schéma (scan de tous les `create table`
  confrontés aux `alter table … enable row level security`).
- **`search_path` épinglé sur toutes les fonctions `security definer`** — la
  classe de faille relevée à 43 exemplaires dans un audit antérieur est fermée.
- **Clé `service_role` strictement serveur** : sa seule occurrence hors
  `lib/supabase/admin.ts` est un message d'erreur ; aucun composant `"use
  client"` ne l'importe ; aucune variable `NEXT_PUBLIC_` ne porte de secret.
- **Signature Stripe vérifiée** avant traitement (`app/api/stripe/webhook/route.ts:17-27`).
- **Retour MonCash confirmé serveur-à-serveur** (`retrieveTransactionPayment`),
  avec limitation de débit par IP contre l'amplification
  (`app/api/moncash/return/route.ts:29-35`), et repli sur le réconciliateur en
  cas d'échec de vérification — jamais de confirmation sur la foi du navigateur.
- **Montant revérifié en base** au moment de la confirmation
  (`supabase/migrations/0027_coupon_consume_on_confirm.sql:63`), y compris le
  montant USD figé au checkout (ligne 76).
- **Ledger append-only** protégé par déclencheur
  (`supabase/migrations/0025_wallet_ledger_guard.sql:16`).
- **Crons protégés** par `CRON_SECRET` sur les cinq points d'entrée planifiés.
- **Aucun `dangerouslySetInnerHTML`** dans tout `app/` et `components/`.
- **Positionnement topup respecté dans le code** : aucun solde acheteur,
  aucun débit de solde au checkout.
- **Images** : `width`/`height` déclarés, `loading="lazy"`, `decoding="async"`,
  `alt` porteur de sens (`components/product-card.tsx:59-67`) — le CLS est
  maîtrisé sans recourir à `next/image`, choix documenté.
- **Polices** en `display: "swap"` (`app/layout.tsx:14,20`).
- **Largeurs fixes** (`min-w-[520px]`, `[640px]`, `[420px]`) toutes confinées
  dans des conteneurs `overflow-x-auto` **et** cantonnées aux écrans
  d'administration — aucun débordement sur les parcours publics.
- **Double soumission** : boutons désactivés pendant l'envoi sur les trois
  formulaires et sur le bouton d'achat.
